## 10/23 (금) ~ 10/26 (월) — 개발 루프와 단계별 머지

```text
코드 작성 → PR 생성 → 리뷰·승인 → (그 단계의 필수 PR이 모두 승인 또는 단계 목표 시각) → 머지 회의 10분 → 머지 → 다음 단계 작업
   ↑                                                                                                              │
   └──────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

머지는 **승인된 PR의 건수가 아니라 단계로** 한다. 기능이 서로 기대고 있어서(로그인 → 규칙 → 입력 → 조회 → 통합), 단계마다 머지하면 `main`이 늘 실제로 돌려 볼 수 있는 상태가 된다.

### 단계별 확정 조건

각 단계는 **아래 PR이 모두 승인되어 머지되면 확정**된다. PR 번호는 [기능별 담당](#기능별-담당--v01-mvp) 표와 같은 번호를 적는다.

| 단계 | 확정 조건 — 필수 PR (기능 번호 · 담당 · PR) | 다음 단계에 필요한 이유 | 목표 |
| --- | --- | --- | --- |
| **1. 기반** | L-01 회원가입 (A) PR #__ · L-02 로그인 (B) PR #__ · L-05 규칙 (B) PR #__ · L-03 과정 설정 (C) PR #__ | 모든 기능이 로그인과 규칙 위에서 돌아간다 | 10/23 |
| **2. 기록** | L-04 수업일 (A) PR #__ · L-05 출결 입력 (B) PR #__ · L-08 리스크 (C) PR #__ | 반 전체 현황과 통합이 실제 기록과 리스크 화면을 쓴다 | 10/24 |
| **3. 조회** | L-09 반 전체 현황 (A) PR #__ | 통합 전에 화면이 모두 갖춰진다 | 10/26 오전 |
| **4. 통합** | L-12 종료 + 메뉴 통합 (C) PR #__ | — | 10/26 오후 (상태 점검 회의 뒤) |

**필수가 아닌 PR**(단계 무관인 L-10·L-11, README 등 문서)은 단계를 막지 않는다. 승인되어 있으면 아무 머지 회의에서나 함께 머지한다.

### 규칙

| 순서 | 규칙 |
| --- | --- |
| 코드 작성 · PR | 각자 자기 이슈의 코드를 작성하고 PR을 만든다 ([CONVENTION 5절](CONVENTION.md#5-pr-rule)) |
| 리뷰 · 승인 | PR이 올라오면 나머지 두 명이 리뷰하고 승인한다. **두 명 모두 승인한 PR을 "승인된 PR"로 본다** |
| ① 머지 회의 | 한 단계의 **필수 PR이 모두 승인되면** 작업 중이라도 머지 회의를 연다. 약 **10분** |
| ② 기한 안전장치 | **단계 목표 시각이 되면** 필수 PR이 다 모이지 않았더라도 머지 회의를 연다. 승인된 것만 머지하고, 늦어진 PR은 다음 단계로 넘긴다. 늦어진 이유는 10/26 상태 점검 회의에서 다룬다 |
| ③ 머지 순서 | **다른 사람이 기다리는 PR을 먼저** 머지한다 (1단계: 회원가입·로그인 → 규칙 → 과정 설정). 한 건씩 머지하고, 뒤 PR에 충돌이 생기면 작성자가 최신 `main`을 pull해 해결한 뒤 다시 push한다 ([CONVENTION 2절](CONVENTION.md#충돌이-났을-때)) |
| ④ 다음 단계 | 머지가 끝나면 모두 최신 `main`을 받아 다음 단계 작업을 이어 간다 |

- 단계를 하루 안팎으로 잡아 브랜치가 오래 살지 않게 한다. 오래 갈수록 충돌이 늘어난다.
- 1~3단계를 **10/26 (월) 오전까지** 마치고, 4단계는 상태 점검 회의 뒤에 한다.
